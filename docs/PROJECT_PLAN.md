# RoboMaster 通用仿真器项目计划

PolarBear 工程交接与发布验收计划　版本 1.0　2026 年 10 月 13 日（UTC+8）

目标是交付一套基于 MuJoCo、可像游戏一样操作的通用 RoboMaster 3v3 与 7v7 仿真平台。队伍能够导入自己的车辆模型、控制器、轮腿强化学习策略、导航、自瞄和客户端，在真实传感器输入与物理执行链上完成比赛，并让另一台电脑按公开文档复现。

当前已有公开独立仓库、自有 RMCS T2 源码与模型、Linux 干净构建，以及原 Qt 客户端显示真实仿真画面的局部证据。完整自瞄闭环仍失败，通用比赛平台尚未验收。首要工作是修复自有 T2 的有效位姿输出与实时链路，再逐级扩展车辆、算法、客户端和比赛规模。

### 交付边界

- 默认组合：polar-rm-simulator + 自有 polar-rm-client + 自有 RMCS T2。算法或模型缺失时明确失败，不静默退回像素基线、旧版本或模拟输出。

- 最终覆盖：完整 3v3、7v7；操作手视角与观战转播分离；人工与自动控制；局域网多人；裁判、弹丸、命中、补给等规则；整场回放和视频。

- 兼容边界：通过公开模型规范和 RobotIO/插件协议接入其他队伍；允许编写适配层，不要求改写仿真核心。任意未经适配的车辆或二进制不能直接视为兼容。

- 平台优先级：Windows 优先；Linux 可作为有可见视频与交互的阶段交付。当前仅有 Linux x86-64 局部验证，不能据此关闭 Windows 或换机验收。

- 规则与场地：优先采用已经正式发布的 2027 资料；未发布部分使用明确标注版本的 2026 资料。规则实现前必须核验来源，本计划不声称已完成最新官方规则调研。

### 必须保留的工程约束

算法只能使用本机传感器和规则允许的裁判信息。敌方真值、理想定位、命中真值只能用于仿真、裁判和隔离的评测。禁止放宽现有门限、刷新旧时间戳或输入真值来掩盖失败。硬件在软件闭环通过后分阶段接入，并具备独立急停和输出限幅。

授权代码范围内，每个可复现阶段保存代码、测试和证据；不擅自合并主分支，不上传密钥、私人标定或未授权素材。

### 计划的使用方式

第 2–3 节冻结需求和接口；第 4 节说明当前成果；第 5–7 节可直接转成任务；第 8 节规定里程碑；第 9–10 节作为验收清单；第 11 节给出版本与成果地址。任务负责人和建议性能指标在启动对应里程碑时确认，不虚构截止日期或已经承诺的指标。

### 范围解释

3v3 开局争夺中心目标属于队伍策略场景，需支持配置和对抗评测；未经规则核验，不写成官方强制规则。动态车辆模型自动适配是待完成能力，已有插件接口和简化车辆不能作为完成证据。训练 RL 或视觉模型不是自动获得授权的后台工作，需先明确数据、资源与目标。


## 3 架构与接口契约

### 真实闭环

MuJoCo 世界与车辆 → 相机、IMU、编码器、点云 → 队伍感知、定位、导航、决策与完整自瞄 → 底盘/关节、云台、射击请求 → 安全与控制权仲裁 → MuJoCo 执行器和实体弹丸 → 装甲碰撞与裁判 → 合法裁判反馈、客户端 HUD 与回放。每一段都须记录输入帧、输出指令和实际生效时刻。

自瞄链包括检测、角点、PnP、跟踪、预测、弹道、射击判据；导航链包括点云/惯导输入、自主定位、规划和底盘控制。仿真核心不替队伍算法补目标坐标或理想位姿。裁判判定必须来自物理事件及选定规则，客户端不能自行加血或宣告命中。

### 三个数据平面

| 平面 | 可见信息 | 隔离要求 |
| --- | --- | --- |
| 选手与算法 | 本车传感器、校准、允许的裁判信息、获得授权的输入与控制权。 | 不暴露敌方坐标、全图真值、命中预知或理想里程计。 |
| 裁判与仿真 | 完整世界状态、碰撞、伤害及规则内部状态。 | 仅以已定义的裁判协议向外发布合法字段。 |
| 观战与评测 | 俯视、转播镜头、真值标签与离线评分。 | 独立权限和通道，不可回流到参赛算法；可记录审计。 |

### RobotIO 与插件契约

每个适配器必须声明协议版本、robot_id、角色、能力、输入传感器、输出模式、模型与配置哈希。接入配置描述关节、执行器、传感器、装甲、云台和发射器映射；采用显式坐标变换与 SI 单位，统一记录 map、base、gimbal、camera 和 lidar 外参。姿态顺序、角度单位、符号、光学坐标轴、限位必须在接口规范中逐项冻结。

消息包含 session/epoch、递增序列、采样时间、仿真时间、单调壁钟、到达时间、有效期和错误码。控制采用带期限的控制权租约与显式 claim/arm/release；断连、超时、失焦、旧帧、无效数值或插件退出均进入安全状态。重连不得复用旧会话射击命令。

保留现有 JSONL 和 HTTP/JSON 入口，扩展版本协商、插件发现、能力协商、错误语义和一致性测试。提供原生进程与 ROS 2 桥；串口兼容作为可选桥接，避免真实协议侵入物理核心。视频传输、状态/HUD、裁判和控制输入分别定义频率、压缩、顺序、背压和掉包策略。

### 时间与可替换性

离线模式可等待算法，固定种子与时间步，用于复现和诊断；实时模式按壁钟期限执行，过期输入被拒绝，不能借离线暂停冒充实时达标。推理与渲染隔离，队列有界并优先保留最新可用观测。插件崩溃不得拖死比赛服务。第二队算法、另一车辆和第二客户端须通过相同契约测试，拒绝按队名硬编码例外。

### 当前首要阻塞

13 次推理未产出接受的 3D 位姿；保存帧诊断确认有 2D 检测。保存帧诊断的两组 PnP 俯仰为约 −36.0146° 与 +59.0600°，超出原允许范围 [−25°, 55°]。源 56 mm 几何投影 54.51 像素，实际 55 mm 灯条投影 53.54 像素，保存渲染约 54 像素；模型角点跨度约 37 像素。现有检查未发现角点顺序、缩放或明显几何错误。合成光学与模型角点域差异是待验证假设，不能直接定为训练根因。

OFFLINE24 用约 22.1 秒壁钟推进 0.942 秒仿真。其传输证据不能替代实时证据。旧 Qt 失败未保留首个错误，后一次成功显示也不能证明原问题仅是订阅顺序。

### 必须防止误报的历史边界

当前 native 适配仍限静止 red_sentry，射击为独立人工通道；车辆简化，导航仍有理想本车里程计和 64 射线，不能称为真实 MID360/SLAM。历史 timing-v5 全场使用旧 40f7，其他 5 车为像素基线；其完成不能替代自有 T2、多车 native 或通用 3v3 验收。


## 5 任务清单 先打通可信闭环

P0 表示阻断当前可信闭环或发布；P1 表示产品范围内必做；P2 表示后续扩展顺序，不表示可以从最终范围中删去。角色为职责占位，需指派实际负责人。新增文件名和测试包是计划交付物，不表示当前已存在。

### T01 冻结接口与验收配置

优先级 P0｜责任角色 架构与测试｜依赖 无

交付：需求 R01–R12 到测试 A01–A15 的追踪表；RobotIO v1、数据隔离表、目标硬件和版本化验收配置。

验收：坐标、时钟、错误、权限和证据字段无歧义；未决指标清单有责任人。

### T02 修复可复现 PnP 输入链

优先级 P0｜责任角色 视觉与仿真渲染｜依赖 T01

交付：保留失败帧；对照官方装甲尺寸、相机标定、灯条/数字板材质、曝光与模型角点；形成逐因素实验与最小修复。

验收：原门限下产生有效位姿并由 T2 跟踪；记录角点误差、重投影误差和拒绝原因。无真值输入、无门限掩盖。

### T03 完成实时调度与性能剖析

优先级 P0｜责任角色 运行时与渲染｜依赖 T01，可与 T02 并行

交付：分段时间账本；硬件渲染路径验证；推理/编码隔离、有界队列和旧帧策略；实时与离线配置独立。

验收：目标机器按原 profile 验证 80/150 ms 机制；记录拒绝率、P95 延迟及 CPU/GPU，不能改时间戳过关。

### T04 贯通自有 T2 原客户端链路

优先级 P0｜责任角色 客户端与自瞄集成｜依赖 T02、T03

交付：实际相机→原 Qt 显示→自有推理→位姿→跟踪→云台执行的逐帧因果日志；随后接入预测、弹道和受仲裁射击。

验收：静止、移动、丢失重捕获目标均能对应实际云台动作；自动与人工射击分别有授权和实体弹丸证据。

### T05 消除角色与状态硬编码

优先级 P0｜责任角色 仿真核心与集成｜依赖 T01、T04

交付：从静止 red_sentry 扩展到模型声明的机器人、移动底盘、多自瞄实例；每车独立命名空间、状态和控制权。

验收：至少两车并行运行真实算法，移动时不再依靠固定车辆限制；单实例失败不串车、不触发未授权射击。

### T06 建立真实闭环回归集

优先级 P0｜责任角色 测试与视觉｜依赖 T02–T05

交付：固定种子、图像/日志/视频、阶段断言和失败码；区分单元、合成、离线、实时及整场结果。

验收：A02–A04、A11 通过；失败包可独立复现。未经完整回归不得把单次截图或检查数写为发布通过。

## 10 指标预设与发布门禁

### 先冻结测试条件 再比较结果

验收配置必须写明 CPU/GPU/内存、操作系统/驱动、MuJoCo/依赖版本、物理步长、相机分辨率与视场、模型、点云参数、车辆数、同时显示的视频流、网络条件、运行时长和随机种子。均值不足以证明实时性，须报告 P50/P95/P99、最大值、样本数及超期比例。

目标场景建议按距离、姿态、速度、角速度、高度、遮挡和光照组成分层测试，不只挑最好的一次。20 Hz 与 4π rad/s 可保留为已讨论的专项压力预设，不将其擅自升级为所有车辆、传感器或最终整场的统一要求。命中率、角点误差、跟踪保持率、定位漂移等阈值由真实任务与配置冻结，未确认前报告实测值和失败分布。

| 指标 | 建议的候选目标 | 约束 |
| --- | --- | --- |
| 实时因子 RTF | 固定目标机整场均值 ≥ 0.95，仿真按实时上限运行。 | 建议值，尚未验证或经用户确认；3v3 与 7v7 分开测。 |
| 操作手视频 | 每个已声明激活的操作手视角 ≥ 25 FPS。 | 建议值；分辨率和视角数量必须同时冻结。当前默认 15 总 FPS 不是该目标已完成。 |
| 交互时延 | 输入发送到物理生效 P95 ≤ 100 ms；采样到显示 P95 ≤ 150 ms。 | 建议值；分别测网络、排队、物理和视频，不能混用时钟。 |
| 自有原 profile | 保留 80 ms native 图像门限与 150 ms 控制窗口语义。 | 现有配置与回归约束，不代表任意队伍的通用硬性性能标准。 |
| 对局与稳定性 | 覆盖完整比赛时长、正常结束/重开及安全故障。 | 时长取冻结规则；连续轮次和允许失败比例在验收配置中确认。 |
