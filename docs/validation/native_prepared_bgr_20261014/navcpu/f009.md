# Navigation Host hot-segment investigation

The actual navigation attempt2 timeout remains an open root cause. This investigation makes no business-source edit and does not start Session, ROS, WSL, GL, native inference or actual simulation. The single saved-input CPU diagnostic was announced before execution, used the original old observation unchanged, and exited zero. Its process completed in about one second; internal diagnostic time was 0.388 s. No deadline was refreshed or observation admitted to act.

## What runs inside the saved interval

In current `rm_match/integrations/pb_wsl_navigation.py`, `exchange_enter` is line 367 and `packet_validated` is line 409. Between them, act checks ready/closed/stop, snapshots the packet with `copy.deepcopy` (373), validates envelope/op/timeout, imports an already-loaded validator, calls `validate_navigation_observation` (403), checks expected generation, caps against the original observation deadline, and rechecks the original Host clock. The complete `_verify` asset/source/spec hash routine is called only in reset (399–400), not act. There is no path mapping, filesystem read, model SHA, pipe write or JSON wire serialization in the act interval. Wire serialization starts after `encode_begin`. Registry imports the validator at module setup, so late RPC 230/282/233 cannot be attributed to its initial Python import without separate evidence.

`navigation_contracts.py` copies the observation again at line 41. It then strictly validates fields/types/identity/calibration, decodes canonical base64 and reencodes for canonicality (28–37), checks every packed point (84–96), and checks each actual IMU sample. Point work scales with point_count up to the existing 40,000-point cap. All these gates remain required. No source/model or control-window gate may be weakened to optimize them.

There is also validation/copy outside this measured Session interval: Runtime public validation and detached custom act input, WslNavigationAdapter.act validation, and final result validation. Their cost cannot be assigned to `exchange_enter→packet_validated` merely because they occur in the same request. The `_phase` bounded memory lock can be contended by reader or snapshot operations, but the saved rows do not measure lock-wait CPU or establish that this caused a tail.

## Saved actual tail evidence

Production actual2: packet segment P50 0.946 / P99 1.414 / max 20.737 ms. The maximum segment is RPC 282, total 71.616 ms. Maximum total RPC 230 is 75.951 ms and has an 18.020 ms packet segment plus 57.016 ms response-wait interval. Production actual3: packet segment P50 0.957 / P99 7.695 / max 19.434 ms; maximum segment and total both occur at RPC 233, total 75.940 ms. Earlier frozen audits retain exact source and input SHA/timestamps. These are elapsed intervals, not evidence of 18–20 ms CPU execution.

The production ledgers do not contain original per-RPC point_count/base64-length/IMU-count or full observation bytes. ROS request records have the original six identity fields and scan-window metadata only. Therefore the micro-input size cannot be asserted equal to the tail frame sizes.

## Single saved-input mechanical diagnostic

Input is the real archived `navigation-sensors-actual-20261013-attempt2-lines4/first_observation.json.gz`: 584 packed points / 11,680 bytes / 15,576 base64 characters / 51 IMUs. All six identity values and old timestamps remain unchanged. One hundred calls per operation, normal GC policy retained:

| Operation | P50 ms | P95 ms | Max ms |
|---|---:|---:|---:|
| Packet deepcopy only | 0.144 | 0.178 | 0.191 |
| Full strict validator, including its deepcopy | 0.592 | 0.705 | 0.944 |
| Current outer-copy plus full-validator segment | 0.776 | 0.974 | 1.721 |

There was one observed generation-0 GC, 0.0247 ms, collected zero objects. No 18–20 ms tail was reproduced. Both detached and validated observations retain the same immutable base64 string identity: deepcopy duplicates container structure, not the large string content.

Windows thread_time/process_time sample increments are predominantly zero or exactly 15.625 ms. The raw values are retained, but they are too coarsely quantized to classify submillisecond CPU time, GIL waiting or individual tail events. Those counters must not be interpreted as a 15.625 ms compute spike. The normal-policy micro GC observation likewise cannot exclude GC elsewhere in the real multi-thread runtime.

## Minimal validation/instrumentation candidates

Root chose not to implement the redundant-copy optimization: it saves approximately 0.14 ms on this saved input, and does not reproduce or explain the tail. A future candidate could shallow-copy only the exact outer wire wrapper and use the full validator's detached return object as wire observation, never the caller alias. That candidate still needs equality-of-values-and-types, caller-after-validation mutation isolation, wrong-generation/deadline, enum/bool/string-subclass and malicious deepcopy-hook regression analysis; none was executed or asserted passed here. Ordinary public/custom inputs remain subject to full strict validation. The source/model/registration SHA checks at their existing startup/reset boundaries remain intact.

For the next actual observation, add scalar fields to the existing bounded `packet_validated` event rather than adding enough new events to truncate the 4,096 cap: clone_wall_s, validation_wall_s, original point_count/base64_characters/IMU_count and sampling-thread ID. Preserve the same original Host clock/deadline and do not store full raw/private data in that diagnostic. A bounded optional GC callback ledger with generation/thread/start/end can reveal overlap, but overlap alone is not proof of causation. Thread CPU counters need platform-resolution validation first; current single-call counters cannot resolve this question. If a tail remains after controlling payload size, only a separately labelled scheduling/GIL trace can identify that mechanism.

This diagnostic did not measure a contention scenario, did not run the real physics/SDK authority and does not prove a timeout repair. The original 80/150 ms and six-identity gates are unchanged. `CPU_DIAGNOSTIC.json`, exact source/input hashes and all measured samples are the auditable boundary of the result.
